# The S3 storage driver

Bakery's byte store has two drivers. `STORAGE_DRIVER=local` writes to
`STORAGE_DIR`; `STORAGE_DRIVER=s3` writes to a bucket. Everything else --
tenancy, refcounts, dedup, retention, the GC -- lives in Postgres and does not
change.

This is the **operator-facing** document for the S3 driver. The invariants it
implements are in `internal/storage/storage.go`'s `Writer` doc and in
`CLAUDE.md`; the ruling that produced them is section 9 of
`docs/design/specs/2026-08-16-feedback-wave-1.md`.

## Configuration

| Flag | Env | Notes |
|---|---|---|
| `--storage-driver` | `STORAGE_DRIVER` | `local` (default) or `s3`. A Kong enum: an unknown value is refused at parse time. |
| `--s3-bucket` | `S3_BUCKET` | Required when the driver is `s3`. |
| `--s3-region` | `S3_REGION` | |
| `--s3-endpoint` | `S3_ENDPOINT` | Set for minio, Ceph RGW, Garage, R2. Leave unset for AWS. |
| `--s3-force-path-style` | `S3_FORCE_PATH_STYLE` | `{endpoint}/{bucket}/{key}` instead of a virtual host. Required by minio and most self-hosted gateways. |
| `--s3-prefix` | `S3_PREFIX` | Optional. Lets one bucket hold several environments. |

**There are deliberately no credential flags.** Credentials come from the
standard AWS chain -- environment variables, the shared config files, IMDS,
IRSA / EKS pod identity. That is the same stance the OCI backend takes for
upstream registry credentials: server-level environment, never a flag and never
plaintext in the database. On EKS this means an IRSA service account and nothing
in a Secret.

Bakery **probes the bucket at boot** with `HeadBucket`, before it binds a
listener. A misspelled bucket, an unreachable endpoint or a credential chain
with nowhere to go is a refused boot with a named error -- never a 500 on the
first cache write, hours later. On Kubernetes, drop `pvc.yaml` and the
`STORAGE_DIR` env var when you switch (see `k8s.md`).

## Bucket layout

```
{prefix}objects/{64hex}    an object, named by the sha256 WE computed
{prefix}staging/{32hex}    a partial or just-finished write
```

No fan-out directories: S3's index is already a sorted key range, and Local's
two levels of 256-wide directories exist only because `readdir` is the GC's
bottleneck on a filesystem.

## Required lifecycle rules

**Two rules. Both are required operator setup, not optimizations.**

```json
{
  "Rules": [
    {
      "ID": "bakery-expire-staging",
      "Filter": { "Prefix": "staging/" },
      "Status": "Enabled",
      "Expiration": { "Days": 1 }
    },
    {
      "ID": "bakery-abort-incomplete-multipart",
      "Filter": { "Prefix": "" },
      "Status": "Enabled",
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
```

(Add your `S3_PREFIX` to both `Prefix` values if you set one.)

Why each exists:

- **`staging/` expiry.** A write stages to `staging/{uuid}` because the digest
  is not known until the last byte is written and `CreateMultipartUpload`
  demands a key up front. Bakery deletes the staging key on a successful
  `Commit` and on `Abort`, but a process killed between the two -- SIGKILL, an
  evicted pod, a node that went away -- leaves it. Nothing ever reads it again.
- **`AbortIncompleteMultipartUpload`.** An interrupted multipart upload leaves
  *parts* that no key lists and no `ListObjects` shows, and you are billed for
  them indefinitely. The SDK aborts its own upload on error; this rule covers
  the case where the process did not survive to do so.

## Orphaned bytes are possible, and they are the tolerated direction

The driver publishes an object at its content address in `Sync`, which runs
**outside** the metadata transaction. `Commit`, which runs **inside** it under
the digest advisory lock, re-asserts the object's presence with one `HeadObject`
and re-copies from the retained staging key if a concurrent garbage collection
deleted it in between.

The operator-visible consequence: a transaction that rolls back after `Sync` --
or a deduplicated write, where `Commit` is never reached -- leaves bytes at a
content address that no `blobs` row names. That is an **orphan**: it costs
storage and nothing else. The direction the ordering invariant forbids is the
opposite one, a live row naming bytes that are gone, which is a permanent 500 on
every future GET; `TestS3_CommitRepublishesAfterAReap` is the gate that holds
that line.

A full orphan sweep (bucket listing reconciled against `blobs`) is **not** built.
It is recorded as GC follow-up work. Until it exists, orphans accumulate slowly
and are safe to ignore; if you want to reclaim them, list `objects/` and delete
what `blobs.digest` does not contain -- **while no writes are in flight**, since
a key can legitimately exist for the moments between `Sync` and the row.

## Minimum IAM policy

```
s3:ListBucket            on arn:aws:s3:::BUCKET          (HeadBucket needs it)
s3:GetObject             on arn:aws:s3:::BUCKET/*
s3:PutObject             on arn:aws:s3:::BUCKET/*
s3:DeleteObject          on arn:aws:s3:::BUCKET/*
s3:AbortMultipartUpload  on arn:aws:s3:::BUCKET/*
```

`PutObject` covers both the staged upload and the server-side copy to the
content address; no separate copy permission exists.

## Performance notes

- **Reads are proxied, never presigned redirects.** A redirect would leak the
  bucket's identity to every build host and would bypass Bakery's authorization
  on the second request.
- **No hand-rolled `Range`.** `ServeObject` already falls into its documented
  `Content-Length` + plain-200 branch for a non-seekable body, which is what
  `GetObject` hands back.
- **All size-proportional work happens in `Sync`**, outside the transaction:
  the upload, and the server-side copy to the content address (an
  `UploadPartCopy` sequence above 5 GiB). `Commit` makes two constant-time calls
  on the common path. `TestS3_CommitIssuesOnlyConstantTimeCallsWhenObjectPresent`
  is the gate; without it, a "simplification" that moves the copy into `Commit`
  would hold a pool connection and the digest lock across seconds of copying and
  starve every other Postgres user.
- **`Delete` is a network round trip**, where the local driver's is a
  sub-millisecond `unlink`. The GC's pending sweep drives up to 1,000 deletes per
  round, one per transaction, so a large sweep moves from sub-second to minutes
  of wall clock. This is inside the per-operation bound and is not a correctness
  problem; batched `DeleteObjects` is recorded GC follow-up work. `Delete` runs
  on a client capped at **2 attempts** rather than the SDK's default retry
  ladder, because it is the one storage call that runs inside a transaction
  holding the digest advisory lock.
- **No defensive read-after-write retry loops.** S3 has been strongly consistent
  for read-after-write, read-after-overwrite and read-after-delete since December
  2020. A retry loop here would be pure latency.

## Testing against a real server

`just storage-conformance` runs the shared, driver-generic suite
(`internal/storage/conformance_test.go`) against both drivers -- the S3 half
against a real minio the harness starts with `docker run` on a
daemon-assigned port. **A skip fails the recipe**: a skipped S3 half means not
one assertion ran against real S3 semantics, and a fake would have agreed with
whatever the driver happened to do.

To point it at your own server instead of the container:

```sh
export TEST_S3_ENDPOINT=http://127.0.0.1:9000
export TEST_S3_ACCESS_KEY=...
export TEST_S3_SECRET_KEY=...
export TEST_S3_REGION=us-east-1        # optional
export TEST_S3_BUCKET=my-scratch-bucket # optional; one is created if unset
just storage-conformance
```
